============================================================
一、这次到底改了什么
============================================================

改之前，页面是一层层往下摞的：

    ┌─────────────────────────────────────┐
    │  墨阁   素材统计   账号              │  ← 顶栏
    ├─────────────────────────────────────┤
    │  搜索框 [上传] [导入] [粘贴]         │  ← 工具栏
    ├────────┬────────────────────────────┤
    │  标签   │  素材列表                  │  ← 主体两栏
    └────────┴────────────────────────────┘

这样只有"一个功能"的时候没问题。但你的规划里有六个功能
（素材库 → 检索 → 分类 → 内化 → 大纲 → 人设卡），
要是每个功能都往顶栏加一排按钮，顶栏会变成杂货铺。

改之后：

    ┌──────────┬──────────────────────────────┐
    │ 墨阁      │  总素材库        [搜索][按钮] │
    │          ├──────────────────────────────┤
    │ 总素材库  │  统计条：素材 / 字数 / 标签 │
    │ 素材检索  ├──────────────────────────────┤
    │ 素材分类  │  标签  │  素材列表           │
    │ 剧情内化  │        │                     │
    │ 大纲生成  │        │                     │
    │ 人设卡    │        │                     │
    │          │                              │
    │ 账号 退出 │                              │
    └──────────┴──────────────────────────────┘
      ↑ 永远只放"有哪些功能"   ↑ 每个功能的页面，互相不干扰

一句话：左边管"去哪儿"，右边管"在那儿干什么"。

这个结构的好处不是好看，是**不打架**。
以后做检索功能，它的搜索框、它的结果列表，全都只待在右边这块，
完全不用动左边，也不用担心把素材库的界面挤变形。


============================================================
二、新布局的骨架：两块并排，各自独立
============================================================

HTML 的结构就三层，非常短：

    <div class="app">                     ← 整个屏幕
      <aside class="nav"> … </aside>      ← 左边：功能导航
      <main class="stage"> … </main>      ← 右边：功能舞台
    </div>

对应的三条 CSS 是重点，逐条看：

    .app   { display: flex; height: 100%; }

      display: flex 的意思是"里面的东西横着排"。
      默认是竖着排（像写文章一行一行往下）。
      加上 flex 就变成左右并排。

      height: 100% 让它撑满整个屏幕高度。

    .nav   { width: 214px; flex: 0 0 214px; }

      宽 214 像素。这一列是"钉子户"：不管右边内容多长多短，
      它永远 214，不伸不缩。

      那两个 0 和 214 分别是：
        flex-grow: 0    → 有多余空间也别长胖
        flex-shrink: 0  → 空间不够也别被压扁
        flex-basis: 214px → 你的基础宽度是 214

      这三个值合起来写在一行，是 CSS 里的简写，等价于：

        flex-grow: 0;
        flex-shrink: 0;
        flex-basis: 214px;

    .stage { flex: 1 1 auto; overflow-y: auto; }

      flex: 1 1 auto 的意思是"剩下多少空间你全拿走"，所以右边自动占满。

      overflow-y: auto 是说：内容比屏幕高的时候，这一块自己出滚动条。

这里有个容易忽略但很重要的细节，在 body 上：

    body { overflow: hidden; }

    为什么要禁止整个页面滚动？
    因为滚动只能有"一个"负责人。如果页面自己也能滚、
    右边那块也能滚，就会出现两个滚动条、滚动位置互相打架的怪现象。

    现在的分工是：
      body        不许滚
      .nav        内容多了自己内部滚（功能很多时用得上）
      .stage      内容多了自己滚 ← 日常滚动都发生在这里

三、左侧栏是怎么"画"出来的（重点）
============================================================

先看左侧栏在 HTML 里长什么样 —— 你会发现它几乎是空的：

    <nav class="navlist" id="navlist"></nav>

对，里面一个字都没有。那六个功能是从哪儿冒出来的？

答案是：JS 里有一张表，页面打开时按这张表"画"出来。
在 frontend/index.html 里搜 VIEWS，能看到它：

    const VIEWS = [
      { id: "library",  name: "总素材库", icon: "library", ready: true,
        desc: "所有素材都在这里" },
      { id: "search",   name: "素材检索", icon: "search",  ready: false,
        desc: "按关键词从素材库里捞出最相关的片段" },
      { id: "classify", name: "素材分类", icon: "tag",     ready: false, … },
      { id: "infuse",   name: "剧情内化", icon: "wand",    ready: false, … },
      { id: "outline",  name: "大纲生成", icon: "list",    ready: false, … },
      { id: "persona",  name: "人设卡",   icon: "user",    ready: false, … }
    ];

这是一个"由字典组成的列表"。每个字典描述一个功能：

    id     这个功能的名字代号，程序用它来认人
    name   显示在左侧栏上的名字
    icon   用哪个小图标
    ready  做完了吗？没做完的显示"待做"
    desc   一句话说明它是干什么的

然后 renderNav() 这个函数把表里的每一项变成一行 HTML：

    box.innerHTML = VIEWS.map(v => {
      …
      return '<button class="navitem" data-view="' + v.id + '">' + … + '</button>';
    }).join("");

.map 是"列表加工机"：给它一个列表，它按你的规则把每一项都变个样，
返回一个新列表（这里是把"字典"变成"按钮的 HTML 文本"）。
最后 .join("") 把那堆文本粘成一大坨，一次性塞进页面。

为什么要这么绕？直接手写六个 <button> 不行吗？

行，但会有两个麻烦：

  第一，改一次要改六处。比如想把"待做"两个字换成"开发中"，
        手写的要改六个地方，容易漏一个。

  第二，漏了不会报错。手写时少一个引号、少一个闭合标签，
        浏览器不吭声，只是显示得怪怪的，你得盯着看半天。

用表 + 循环，这两件事都解决了：改一处，六处一起变。

这种写法有个名字，叫"数据驱动"——
界面长什么样，由数据决定，而不是由你手打的 HTML 决定。
你以后会经常听到这个词，其实就这么回事。

四、以后加一个新功能，具体改哪几行
============================================================

这是这一节最实用的部分。假设一个月后你要加"章节管理"这个功能。

第 1 步：打开 frontend/index.html，找到 VIEWS，加一行：

      { id: "chapter",  name: "章节管理", icon: "list",    ready: false,
        desc: "把素材拼成章节，管理写作进度" },

  加完刷新页面，左侧栏最下面就会多出"章节管理 · 待做"。
  点它，右边会显示占位页。**这一步不用写任何新代码。**

第 2 步：真正做这个功能时，把 ready 改成 true：

      { id: "chapter",  name: "章节管理", icon: "list",    ready: true,
        desc: "把素材拼成章节，管理写作进度" },

  同时，在 HTML 里加一块属于它的页面：

      <section class="view" id="view-chapter">
        …这里写这个功能自己的界面…
      </section>

  注意 id 必须是 view- 加上 VIEWS 里的 id。
  这条约定写在 goView() 函数里：

      const target = v.ready ? id : "soon";
      document.querySelectorAll(".view").forEach(el => {
        el.classList.toggle("on", el.id === "view-" + target);
      });

  翻成人话：View 表里说这个功能做好了，就显示名字叫 view-<id> 的那块；
  没做好，就显示占位页。

第 3 步：如果它需要自己的按钮（比如"新建章节"），
        就写在那块 <section> 里，别往左边栏或全局顶栏塞。

就这样。三步，而且第一步永远只用改一行。

如果你想要一个新图标，去 ICONS 那张表里加一条：

    chapter: '<path d="…"/>'

图标用的是 SVG（矢量图），本质是"画线的指令"：
M 是"笔移到某处"，L 是"画直线到某处"，一条条连起来就成了图形。


============================================================
五、顺手讲清 flex 布局里最容易绕晕的几件事
============================================================

flex 是排版的工具，但新手常被几个概念绊住，一次说清。

（一）横排还是竖排，由 flex-direction 决定

    .app      { display: flex; }                    → 横着排（左导航 + 右舞台）
    .navlist  { display: flex; flex-direction: column; }
                                                    → 竖着排（六个功能上下叠）

    默认是"横着排"（row）。想竖排就必须显式写 column。

（二）flex-grow 是"分剩下的空间"

    假设容器宽 1000，两个孩子一个 200、一个想自己定：
      flex-grow: 0 → 分剩的时候没你的份，就 200
      flex-grow: 1 → 剩下的 800 全给你，你变 1000

    这就是为什么 .stage 用 flex: 1 1 auto 就能自动占满右边 ——
    它是在说"左边那个是钉子户，剩下的都归我"。

（三）两边都设 flex: 1 会怎样？

    会平分。左边 500 右边 500。
    这就是为什么我特意给 .nav 写 flex: 0 0 214px ——
    如果不写，它会跟右边一起平分，导航栏会变宽得莫名其妙。

（四）flex-wrap: wrap 是"放不下就换行"

    .vhead 里用了它。但换行有时不是你想要的 ——
    这次就踩到了，见下一节。

（五）一个口诀

    谁固定，就给它固定的宽度 + flex: 0 0 <宽度>；
    谁该灵活，就给它 flex: 1 1 auto。
    剩下的交给浏览器算。

六、"占位页"这个设计为什么值得做
============================================================

还没做的功能，点进去不是弹一句"敬请期待"，而是显示一整页，
上面写清楚：这个功能是干什么的、为什么还没做、跟其他功能的先后关系。

理由有三个：

  1. 让人知道"这是计划，不是坏了"。
     一个灰着的菜单项点下去什么都没发生，用户会以为网站有 bug。

  2. 把路线图摆出来。占位页上写着
     "左侧栏从上到下的顺序，就是开发顺序"，看一眼就懂。

  3. 逼自己把话说清楚。
     写 desc（一句话说明这个功能干什么）的时候，
     如果写不清楚，说明还没想明白，那就先别做。

在代码上，它只是一块普通的页面，由 goView 动态填内容：

    document.getElementById("soonName").textContent = v.name;
    document.getElementById("soonDesc").textContent = v.desc;

所以你加进 VIEWS 的每一条，都会自动获得一个像样的占位页。

七、这次修掉的两个 bug
============================================================

bug 1：工具按钮莫名其妙换行

    现象：右上角的「搜索框 + 上传 + 导入 + 粘贴」四个东西，
          明明一条放得下，却挤成了两行。

    原因：我把操作区写成了

        .vacts { margin-left: auto; }

          margin-left: auto 的作用是"把左边的空白全吸走"，
          这样这块东西就被推到最右边。

          但它是 flex 布局里的一个孩子，而 flex 算宽度时，
          它拿到的是"内容宽度"，浏览器对这个宽度的估算
          跟实际渲染不完全一致，算窄了 → 于是内部换行。

    修法：不用 auto 边距去"推"，改成用布局规则去"撑"：

        .vacts {
          flex: 1 1 auto;             ← 吃掉整条剩余宽度
          justify-content: flex-end;  ← 里面的东西靠右对齐
        }

    区别很关键：
      margin-left: auto 是在"推"自己
      flex: 1 + justify-content 是在"占满 + 内部对齐"

    后者宽度是明确的，浏览器不会再算错。

    这条经验可以记下来：**别用 auto 边距来布局，
    要占满就用 flex: 1，要对齐就用 justify-content。**

bug 2：深色底上的虚线圈看不见

    现象：左侧栏被选中的那一项是深色背景，
          它右边的"待做"徽章是深色虚线圈 + 灰字，
          在深色背景上几乎消失。

    原因：徽章的颜色是"给浅色背景定的"，碰上深色底就不成立。

    修法：给"选中状态下的徽章"单独定一条：

        .navitem.on .soon {
          color: rgba(255,255,255,.8);
          border-color: rgba(255,255,255,.4);
        }

    rgba 是"带透明度的颜色"，四个数字分别是红、绿、蓝、透明度。
    rgba(255,255,255,.8) 就是白色、80% 不透明。

    这类 bug 有个共同点：**它不在逻辑里，而在状态组合里**。
    代码没错，只是"两种状态碰在一起"没考虑过。
    排查时要多问一句：这个元素在别的状态下长什么样？

八、一个只有我自己会踩的坑：截图拍到了"半成品"
============================================================

这一节跟写代码关系不大，但方法值得学。

我做界面验证的方法是：用没有界面的浏览器打开页面、截图，然后看图。
这次截图发现"左侧栏的高亮没跟着切换"，我以为代码写错了。

但我没有直接去改代码，而是先把"浏览器跑完之后的页面结构"打印出来：

    那个命令会输出整页的 HTML。
    我查了导航按钮的 class，结果是：

        class="navitem off on"   data-view="outline"

    意思是：**代码是对的**，高亮已经切到"大纲生成"了。

    那为什么图上是旧样子？

原因是截图这个动作和页面重绘之间有极短的时间差。
浏览器的流程是：

    改 class（瞬间）→ 浏览器算新样式 → 画到屏幕上

    中间那两步要花一点点时间。截图如果正好卡在
    "class 改了、屏幕还没重画"的这一瞬间，拍到的就是旧画面。

修法有两个，一起用最稳：

    1. 让页面改完之后多等一下再拍
    2. 给浏览器加一个参数，要求它"把所有该画的都画完再截"

这件事本身的道理，比这个 bug 更值得记住：

    **当你觉得"代码明明对但结果不对"，不要凭感觉猜，
      去把中间状态打出来看。**

    我如果当时凭感觉去改代码，很可能会把本来正确的逻辑改坏，
    然后在错误的方向上越走越远。

    "先量，再猜" 这四个字，值一个小时的加班。

九、测试脚本的重要改动（这条跟你的数据安全有关）
============================================================

这次发现一个真问题，必须讲清楚。

项目里有两个测试文件：

    tests/test_auth.py    单元测试，直接调用代码里的函数
    tests/smoke_test.py   接口测试，通过网址（HTTP）调用，整个流程跑一遍

上一次我给测试加了"隔离"：让它用临时数据库，不碰你的真实数据。
但这次我发现 —— **只隔离了单元测试，漏了接口测试**。

为什么漏了很难发现？

    接口测试是通过网络请求去测的，它自己并不直接打开数据库，
    真正打开数据库的是"正在跑的那个墨阁服务"。
    而那个服务连的是哪个数据库，是由**启动它的那一刻**决定的。

    所以我在测试脚本里设一个环境变量"请用临时库"，对已经跑着的服务
    毫无影响 —— 服务照样连你的真实库。

    结果就是：这个测试会在你的真实库里注册测试账号、造测试数据、
    跑完再删掉。虽然它每次都会清理干净，
    但万一中间崩了，垃圾就留在你库里了。

修法：让测试脚本**自己**起一个服务。

    1. 建一个空的临时数据库（不在 data/ 目录里）
    2. 用这个临时库、在一个随机端口上，自己启动一个墨阁服务
    3. 测完把这个服务关掉、临时库删掉

    这样它跟你的真实数据完全不接触。
    附带的好处是：以后跑测试不用先双击「启动墨阁.bat」了，
    直接跑测试脚本就行。

另外加了一道"保险" —— 这段代码值得单独看一眼：

    def verify_isolated(expected_dir):
        h = call("GET", "/api/health")
        dbp = os.path.abspath(h.get("db", ""))
        return (os.path.abspath(expected_dir) in dbp), dbp

它在测试开始前问服务一句："你用的数据库文件在哪儿？"
如果那个路径不在临时目录里，脚本就**直接停下来**，不测了。

    为什么要这么做？因为"隔离失败"这件事，
    从测试结果上是看不出来的 —— 它照样全绿通过，
    只是在删你的真实数据。

    所以这种事不能靠"应该没问题"，得写一句断言去验。
    宁可这次不测，也不能删错东西。

现在跑测试，你会先看到这样几行，说明隔离生效了：

    正在准备隔离环境（临时库 + 独立端口）…
      临时数据库目录：C:\Users\…\Temp\moge_smoke_xxxx
      服务用的数据库：C:\Users\…\Temp\moge_smoke_xxxx\moge.db
      隔离检查：通过（你的真实数据不会被碰）

怎么跑：

    cd G:\docker\moge
    .venv\Scripts\python.exe tests\smoke_test.py

今天最该记住的三句话
============================================================

  1. 界面长什么样，交给数据决定（VIEWS 那张表），
     不要靠手写一大片 HTML。

  2. flex 布局：谁固定就给 flex: 0 0 固定宽，
     谁灵活就给 flex: 1 1 auto。
     别用 auto 边距布局，用 flex: 1 + justify-content。

  3. 测试要碰数据的，必须能证明自己碰的是临时数据，
     证明不了就别跑。
