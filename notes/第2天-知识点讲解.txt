墨阁 · 第 2 天知识点讲解
本轮做了什么：给网站加了「账号」，并让素材在网页上上传入库
================================================================


〇、先回答你最关心的那句：素材到底存在哪里

一句话：存在你自己电脑上的一个文件里。

    G:\docker\moge\data\moge.db

这是个 SQLite 数据库文件。SQLite 的特点是：整个数据库就是磁盘上的一个文件，
不需要装数据库服务器、不需要开端口、不需要账号密码。
（MySQL、PostgreSQL 那种要单独装一个服务、常驻在后台跑；SQLite 不用。）

它已经被 .gitignore 挡住了，所以不会跟着代码传到 GitHub。
另外 data/ 这个目录整个都是排除的，将来你往里放任何东西都不会被传上去。

下面把"素材从你手里到数据库里"这一路拆开讲。


================================================================
一、素材的三层结构
================================================================

一份素材在你的系统里会经历三个地方，理解这三层，你就理解了整个网站：

    第 1 层【你的电脑上】
        桌面上那个 外貌.docx
        这是"原件"，墨阁从头到尾不会修改它。

    第 2 层【文件】
        G:\docker\moge\data\moge.db
        一个文件，装着所有素材的正文和标签。
        这个文件是"总仓库"。

    第 3 层【数据库里的表】
        moge.db 这个文件内部，又分成了几张表。
        真正存字的地方叫 materials 表的 content 那一列。

打个比方：
    moge.db  = 一个档案柜
    表       = 柜子里的抽屉（素材一个抽屉、标签一个抽屉、账号一个抽屉）
    一行     = 抽屉里的一张卡片
    一列     = 卡片上的一个栏目（标题、正文、字数、存的时间……）

为什么要有"层"这个概念：因为将来出问题时，你可以一层一层往下查。
    页面上看不到某条素材
    → 先看它是不是被你筛掉了（第 3 层之上，只是没显示）
    → 再看数据库里到底有没有这一行（第 3 层）
    → 最后才怀疑是不是导入时就没读出来（第 1 层到第 2 层之间）


================================================================
二、数据库里到底长什么样
================================================================

现在总共有五张表。三张管素材，两张管账号。

--------------------------------------------------
2.1 materials —— 素材本体（最重要的一张）
--------------------------------------------------

一行 = 一份素材。关键栏目：

    id           编号，自动递增。1、2、3…… 每份素材的唯一身份
    owner_id     归属谁。见下面第六节
    title        标题
    content      正文（你导入的那些字，真正就存在这里）
    chars        字数
    ext          扩展名，.docx / .txt
    source_path  从哪来的（文件路径，或者"（上传：xxx.txt）"）
    content_hash 内容指纹，用来判断"这份是不是已经存过了"
    local_only   是否"仅本地"（1 = 将来不送云端）
    note         解析时留下的提示（比如"编码识别为 utf-8"）
    created_at   存进来的时间
    updated_at   最后修改时间

两个栏目值得单独说：

    content_hash（内容指纹）
        把正文用 MD5 算成一串 32 位的字符。内容一样，算出来就一样。
        导入前先查这串指纹有没有出现过 —— 有就跳过。
        注意：它算的是"内容"，不是文件名。
        所以你把 外貌.docx 改名成 外貌2.docx 再导一遍，照样认得出来是同一份。

    owner_id（归属）
        这条是"谁的东西"。第 3 天会讲它怎么把不同账号隔开。

--------------------------------------------------
2.2 tags —— 标签
--------------------------------------------------

一行 = 一个标签名。比如「外貌」「打斗」「世界观」。

为什么不直接在素材上写"外貌,打斗"这样一串文字？
    因为标签和素材是"多对多"关系：
        一份素材可以有多个标签
        一个标签下可以有多份素材
    用一张单独的表才能表达清楚，也才能算"这个标签下有 3 份素材"。
    写成逗号串的话，将来想查"含某标签的素材"只能靠字符串模糊匹配，很容易错。

--------------------------------------------------
2.3 material_tags —— 中间表
--------------------------------------------------

它只有两列：material_id 和 tag_id，一行 = 一个"挂载关系"。

    第 1 行：素材 3 挂了标签 5
    第 2 行：素材 3 挂了标签 9

这叫"中间表"，是数据库里表达多对多关系的标准做法。
第三张表的代价是查询时要多 JOIN 一次，换来的是数据不会乱。

--------------------------------------------------
2.4 users —— 账号（本轮新增）
--------------------------------------------------

    id             编号
    username       用户名（唯一，不能重名）
    password_hash  密码搅碎后的结果（注意：不是密码本身！）
    salt           这账号专用的"盐"
    created_at     注册时间
    last_login_at  最后一次登录时间

--------------------------------------------------
2.5 sessions —— 登录凭据（本轮新增）
--------------------------------------------------

    token       一串随机字符，等于"门票"
    user_id     这张票是谁的
    created_at  什么时候发的
    expires_at  什么时候过期

--------------------------------------------------
怎么自己看这些表（不用装任何软件）
--------------------------------------------------

在 G:\docker\moge 目录下开一个命令行，敲这两行：

    .venv\Scripts\python.exe backend/db.py

这会打印：数据库位置、素材数、总字数、标签数、账号数。最常用的就这一条。

想看更细的内容，用这一行（把 sql 里那句话换掉就行）：

    .venv\Scripts\python.exe -c "from backend import db; c=db.connect(); print([dict(r) for r in c.__enter__().execute('select id,title,chars,owner_id from materials limit 5').fetchall()])"

看不懂那串代码没关系，第 5 天会讲到它。
现在你只要知道：有个命令能直接把数据库里的东西打出来看。


================================================================
三、账号系统：为什么密码不能直接存
================================================================

这是本轮最值钱的一个知识点，面试也爱问。

--------------------------------------------------
3.1 直接存密码的三个后果
--------------------------------------------------

假设直接把密码明文存进数据库：

    一、数据库文件被人拷走 → 所有人的密码全泄露
    二、你是写小说的人，很多人各个网站用同一个密码
        → 你这边泄露，别人的邮箱、支付账号跟着遭殃
    三、连你自己都不该看到用户的密码。你不知道，就泄露不了

所以真实存进去的是"密码搅碎之后的结果"。

--------------------------------------------------
3.2 哈希（搅碎）
--------------------------------------------------

    密码 + 盐  →  [搅碎函数]  →  一串固定长度的乱码

    存这串乱码。登录时把用户输入按同样方式搅碎，比对两串乱码是否相同。

关键性质：搅碎是单向的。能从密码算出乱码，不能从乱码倒推回密码。

墨阁用的是 pbkdf2_hmac，它属于 Python 自带的标准库（hashlib），
不用额外装任何东西。输出固定 64 位十六进制字符。

--------------------------------------------------
3.3 盐：让同样的密码搅出不同结果
--------------------------------------------------

问题：如果只是"密码 → 搅碎"，那两个人密码都是 123456，
      搅碎结果就一模一样，一眼能看出"这两人密码相同"。

加盐解决这个：给每个账号单独生成一段随机字符串（盐），
搅碎时掺进去。

    账号 A：123456 + 盐 a1b2c3  → 搅碎 → 4f9d...（结果一）
    账号 B：123456 + 盐 x9y8z7  → 搅碎 → b23e...（结果二）

同样的密码，结果完全不同。

盐不需要保密，就明文存在 users 表里。它的作用不是"藏起来"，
而是让"同一密码"变得看不出来，同时让攻击者没法用一张
"常见密码对照表"批量反查所有账号。

生成盐用的是 secrets 模块，不是 random：
    random 是给"抽奖、洗牌"用的，结果可以被推算规律
    secrets 是给"密钥、密码"用的，密码学安全
凡是沾安全的地方，一律用 secrets。

--------------------------------------------------
3.4 为什么故意让它慢
--------------------------------------------------

搅碎函数可以被暴力试。一次普通 MD5 一秒能试几十亿次。

所以墨阁用的是"故意慢"的算法：跑一次要花约 0.05 秒（20 万轮迭代）。

    正常登录你感觉不到（就慢这一下）
    想暴力穷举就慢了千万倍，不划算了

这是个很反直觉的设计：通常我们追求程序快，但密码这里故意求慢。
记住这句话就够了 —— 慢在这里是安全特性，不是性能问题。

--------------------------------------------------
3.5 比对密码时的"时序攻击"
--------------------------------------------------

比对两串字符时，如果用普通的"等号"比较，程序发现第一个字符不同
就立刻返回。于是：

    "第 1 位就错了"  →  返回得快
    "前 10 位都对"   →  返回得慢一点

攻击者能测量响应时间，一个字符一个字符地猜出正确答案。
这叫时序攻击。

墨阁用的是 hmac.compare_digest：它从头到尾把所有字符都看一遍，
不管第几位不同，耗时都一样大，堵住这条路。


================================================================
四、登录状态：服务怎么记住"你是谁"
================================================================

网页有个天生的特点：每次请求都是独立的，服务不记得上一秒谁来过。
（这叫 HTTP 无状态）

所以需要一张"门票"。

--------------------------------------------------
4.1 门票
--------------------------------------------------

登录成功时，服务端：

    1. 生成一串随机字符串 token（32 字节随机数）
    2. 把它连同 user_id、过期时间存进 sessions 表
    3. 通过响应头把它塞进浏览器的 Cookie

浏览器拿到 Cookie 后，**之后每次请求都会自动带上它**（这是浏览器
自己的行为，不需要网页代码做什么）。

服务收到请求 → 从 Cookie 里取出 token → 查 sessions 表 → 知道你是谁。

token 本身就是凭证，等于密码。所以：
    用 secrets 生成，不能用 random
    必须带有效期（墨阁是 30 天）
    存在数据库里，退出登录就删掉

--------------------------------------------------
4.2 Cookie 的几个设置，每个都在防一件事
--------------------------------------------------

    HttpOnly      网页里的 JS 读不到这个 Cookie。
                  万一页面被注入恶意脚本，脚本也偷不走这张票。
                  （你在浏览器控制台敲 document.cookie 是看不到它的）

    SameSite=Lax  别的网站替你发请求时，浏览器不会带上这张票。
                  防 CSRF —— 防止别人做个假页面，骗你点一下就把素材删光。

    Max-Age       到期自动失效，不用服务端记着清理。

    Path=/        整个站点都带上它。

还有一个参数叫 Secure（只在 https 下才发这张票）。
墨阁现在是 http://localhost 本地跑，开了会导致"登录成功却始终没登录"，
所以暂时没开。将来真的上线换成 https，要记得打开它。

--------------------------------------------------
4.3 前后端分工：为什么接口必须自己认出你是谁
--------------------------------------------------

这一条是安全意识的核心：

    错的做法：前端把用户名传给后端，后端按这个用户名查素材。
    后果：    用户在前端把用户名一改，就能读走别人的素材。

    对的做法：服务端只信自己发出去的门票，一个字都不听前端的。

墨阁就是这么做的。前端从头到尾没有"告诉后端我是谁"，
它只是带着浏览器自动附加的 Cookie 去请求，后端自己从票里认。

落到代码上，就是每个素材接口多了一个参数：

    user: dict = Depends(auth.current_user)

Depends 是 FastAPI 的"依赖"机制：进接口之前先跑 current_user，
它没登录就直接返回 401，接口函数根本不会被执行。

好处是"必须登录"这件事只写了一遍，所有接口自动都有。
而且前端只要看到 401，就自动弹回登录页 —— 也是只写一遍。


================================================================
五、上传一个文件，路上发生了什么
================================================================

你在网页上把 外貌.docx 拖进去，到它出现在列表里，中间走了六步。

--------------------------------------------------
第 1 步：浏览器把文件装箱（multipart 格式）
--------------------------------------------------

浏览器不能直接把文件对象发给服务器，要按 HTTP 的规矩"装箱"。
这个格式叫 multipart/form-data，长这样：

    --分隔线
    Content-Disposition: form-data; name="files"; filename="外貌.docx"
    Content-Type: application/octet-stream

    （这里是文件的原始字节）
    --分隔线--

每次上传，浏览器现场生成一条随机的"分隔线"，
用它把多个文件隔开。服务端就按这条线切开，还原出一个个文件。

前端代码里对应这几行：

    const fd = new FormData();
    list.forEach(f => fd.append("files", f));
    fetch("/api/upload", { method: "POST", body: fd })

注意：浏览器**拿不到你磁盘上的真实路径**，这是浏览器的安全设计
（否则网站就能知道你电脑的目录结构了）。
所以上传这种方式，不能像"导入文件夹"那样自动用文件夹名当标签。

--------------------------------------------------
第 2 步：后端先把文件落到一个临时文件
--------------------------------------------------

服务端收到字节后，写到 data/tmp/ 下一个临时文件。

为什么要落盘、不能直接在内存里处理？
    因为 docx / pdf / xlsx 这些格式是"压缩包"，解析库需要
    一个真实的文件路径才能打开。
    落到磁盘再调用已有的解析逻辑，能避免为"上传"再写一套解析。

这里有个细节：落盘用的文件名是**随机生成的**（如 a372da9b...txt），
不沿用你上传的文件名。

--------------------------------------------------
第 3 步：文件名必须消毒（防路径穿越）
--------------------------------------------------

假设有人上传的文件名是：

    ..\..\..\Windows\System32\某个系统文件.txt

如果直接拿这个字符串去拼落盘路径，就等于让别人决定往你磁盘的
哪个位置写文件。这叫路径穿越，是最经典的攻击之一。

墨阁的处理是 _safe_name()：只取文件名最后一段，路径部分全部丢掉，
再挡掉几个 Windows 上不合法的字符。

测试里专门有一项验证这件事：

    [通过] 危险文件名被消毒  处理成：坏东西.txt

--------------------------------------------------
第 4 步：交给自己写的解析器
--------------------------------------------------

parsers.py 按扩展名选对应的解析方式：

    .txt / .md    直接读（会自动试几种编码，中文不乱码）
    .docx         解 zip 读里面的 word/document.xml
    .xlsx         读表格单元格
    .pdf          抽文字层

返回的是一个统一格式的字典，长这样：

    {"ok": True, "text": "……正文……", "chars": 34, "ext": ".docx", "note": "……"}

统一格式的好处：后面的代码不需要知道"这是 docx 还是 pdf"。

--------------------------------------------------
第 5 步：入库
--------------------------------------------------

调 db.save_material()，做四件事：

    1. 算内容指纹，查库里有没有 —— 有就返回"重复"，不重复存
    2. 插一行进 materials 表
    3. 把标签挂进 tags 和 material_tags 表
    4. 顺手清掉"没有任何素材在用"的空标签，避免标签栏越积越脏

--------------------------------------------------
第 6 步：删掉临时文件
--------------------------------------------------

素材已经入库，临时文件没用了，删掉（正文属于隐私，不该在磁盘上留副本）。

这一步有个坑，这轮真踩到了，见第九节。


================================================================
六、素材归属：owner_id 是怎么隔离用户的
================================================================

这是本轮另一个核心设计。

--------------------------------------------------
6.1 归属标记长什么样
--------------------------------------------------

    __u7       第 7 号账号的素材
    local      还没有归属的素材

为什么加 __u 前缀，不直接用 "7"：
    翻数据库的时候，"7" 这种裸数字肉眼看不出含义，
    加个前缀一眼能分清"这是第 7 号用户的"还是"这是没归属的"。

--------------------------------------------------
6.2 隔离是怎么生效的
--------------------------------------------------

每个素材接口都从登录门票里取到用户，然后：

    db.list_materials(owner=user["owner"])
    db.stats(owner=user["owner"])

所有查询都带 owner 条件。于是：

    账号 A 的列表里只有 A 的素材
    账号 B 搜索时搜不到 A 的内容
    账号 B 想删 A 的素材，接口返回 404（"没有这条素材" —— 对它来说确实没有）

这三条测试里都验证过。

--------------------------------------------------
6.3 为什么从第一天就该带这个字段
--------------------------------------------------

你可能会想：现在只有我一个人用，加 owner_id 干嘛？

因为将来上线后再加，意味着：
    已有的所有素材都要重新指定归属
    所有查询语句都要改
    tags 表也要跟着改（标签也是分用户的）

等于把已经能用的东西推翻重做。所以这个字段从第一天就留着，
哪怕当时用不上。这叫"为将来的自己省事"。

同类设计还有两个：
    content_hash  从第一天就用来去重
    local_only    从第一天就留着（将来送云端时自动跳过这些素材）

--------------------------------------------------
6.4 你现有的素材现在是什么状态
--------------------------------------------------

你早期是用命令行导入的，那时候还没有账号，
所以它们的 owner_id 是 local —— 也就是"还没有归属"。

注册账号时可以勾选"把之前导入的 N 条素材转到这个账号名下"。
勾了就归你，不勾就还留在未分配状态，之后也能在素材库空的时候
点按钮接收。

为什么不自动帮你转：
    搬动已有数据这件事，应该由你明确点一下，不该我替你决定。
    这是数据安全的基本礼貌。


================================================================
七、这一轮改了哪些文件，逐个说清楚
================================================================

--------------------------------------------------
7.1  backend/db.py（改动：加了用户表与会话表）
--------------------------------------------------

新增两张表：users、sessions。

新增这些函数：

    count_users()                 一共几个账号
    create_user(名字, 哈希, 盐)    建账号，重名返回 None
    get_user_by_name(名字)         按名查（登录用，会带出哈希和盐）
    get_user(编号)                 按编号查（不带密码信息，能安全返回前端）
    touch_last_login(编号)         记一下"刚登录过"

    create_session(票, 编号, 到期)  发门票
    get_session(票)                拿门票换人（含过期判断，过期顺手删掉）
    delete_session(票)             退出登录
    purge_expired_sessions()       清过期门票

    adopt_owner(旧归属, 新归属)     把未归属素材接到某个账号名下

另外把数据库目录改成可以用环境变量 MOGE_DATA_DIR 覆盖。
这一条是给测试用的后门，见第九节。

注意这一层的定位：它只知道"哈希"和"盐"这两个词，
不知道密码是什么、不知道怎么算。算密码的事全在 auth.py。
这么分是为了将来想换加密算法时，只改 auth.py，数据库这层不用动。

--------------------------------------------------
7.2  backend/auth.py（新文件）
--------------------------------------------------

按功能分四块：

    一、密码
        make_salt()                    生成随机盐
        hash_password(密码, 盐)        搅碎
        verify_password(...)           比对（用 compare_digest 防时序攻击）

    二、校验规则
        check_username(名字)           2-20 字符，中文/字母/数字/下划线/连字符
        check_password(密码)           至少 6 位

    三、门票
        new_token()                    生成随机门票
        expires_at_str()               算过期时间
        set_login_cookie(响应, 票)      把票塞进浏览器
        clear_login_cookie(响应)        删票

    四、认出请求是谁
        optional_user(请求)            有登录就返回用户，没有返回 None
        current_user(请求)             必须登录，否则 401

一个细节：check_username / check_password 是"返回错误提示语"而不是抛异常。
这是风格选择 —— 校验失败是预料之中的正常情况，不是程序故障，
用返回值表达，由接口层决定怎么告诉用户。

另一个细节：登录失败时故意不区分"用户名不存在"和"密码不对"，
统一回一句"用户名或密码不对"。
分开提示的话，别人就能拿它当探测工具 —— 一直试用户名，
看到"密码不对"就说明这个用户名存在。这叫用户名枚举。

九、这一轮踩到的坑（包括我自己犯的错，一并说清）

--------------------------------------------------
坑 1（我犯的，比较严重）：测试删掉了你的真实素材
--------------------------------------------------

发生了什么：
    我先写了 tests/test_auth.py 里一项"认领素材"的测试。
    它调用 adopt_owner 把"未归属的素材"搬到一个测试账号下 ——
    当时库里未归属的素材，就是你的那批素材。
    测试结束时按惯例清场，把这个测试账号名下的东西全删了，
    于是你的素材跟着一起没了。

为什么测试全绿还是出事了：
    因为测试本身跑通了 —— 它做的正是它该做的事。
    错的是"它不该在真实数据库上做这件事"。
    这类事故在工业界有个名字：测试污染了生产数据。

怎么修的（三层防护）：
    第一层  db.py 允许用环境变量 MOGE_DATA_DIR 改写数据库位置
    第二层  test_auth.py 在导入 db 之前，把数据目录指到系统临时目录。
            于是它从头到尾没打开过你的真实库。
    第三层  测试开头加了一道保险：核对数据库路径，
            万一环境变量没生效，直接中止，绝不带病运行。

怎么恢复的：
    好在你的素材源头 —— 桌面上那个「分类」文件夹 —— 一直是完好的，
    从源头重新导入一次就完整恢复了（文件数、字数、标签全部一致）。

这一条的教训值得记住：
    "测试能力"和"测试安全"是两件事。
    一个会改数据的测试，必须先把它关进一个一次性的沙箱里。


--------------------------------------------------
坑 2：删临时文件时被运行环境拦住，导致上传报 500
--------------------------------------------------

发生了什么：
    上传时最后一步是删掉临时文件（os.remove）。
    在这个开发环境里，它给 Python 的删除操作套了一层"安全策略"，
    拦下来时抛出的不是普通的 Exception，而是 SystemExit。
    原来的代码只 catch 了 OSError，接不住，于是整个上传报 500。

怎么修的：
    把 catch OSError 改成 catch BaseException，并且注释写清理由：
    素材此时已经入库了，"删不掉临时文件"是无关紧要的小事，
    绝不能因为它把整个上传判成失败。

另外加了"启动时清一遍 data/tmp"：
    素材正文属于隐私，不该在磁盘上越积越多。
    即使某次删除没成功，下次启动也会清掉。

顺便说个判断经验：
    一个 500 错误，第一件事是去看服务端的日志。
    浏览器只会说"请求失败 500"，真正的原因（哪一行、什么异常）
    只在服务端日志里。这轮就是靠日志一眼看到 os.remove 那一行。


--------------------------------------------------
坑 3：CSS 少了一个大括号，后面三条规则全失效
--------------------------------------------------

发生了什么：
    .drop { ... } 这个样式块漏了闭合的 }，
    于是紧跟它后面的 .drop b、.drop span、.drop em 三条规则
    被浏览器当成"上一个块的属性"整个丢掉，
    表现是拖放区里的标题和说明挤在同一行、没有大小层次。

为什么难发现：
    虚线框、内边距这些"更前面"的样式都是好的，
    所以就以为是文字样式本身写错了，而不会想到是"括号没闭合"。

怎么定位的（这招值得记）：
    1. 用无头浏览器截图，看出"哪里不对"
    2. 把那一小块区域裁下来放大，确认到底哪里不对
    3. 回头读 CSS 那一小段，一眼看到少了 }

CSS 的括号错误有个特点：报应不会出现在出错的地方，
而是出现在它后面。所以看到一个样式莫名失效，
先往上翻，看前面那个块是不是没闭合。


--------------------------------------------------
坑 4：无头截图时，导航到"一模一样的 URL"不会重新加载
--------------------------------------------------

我的截图脚本想让页面"登录后刷新一下"，于是写：

    location.replace(location.pathname + location.hash)

结果 URL 跟当前完全相同 —— 浏览器认为这是"同一个地址"，
只触发 hashchange，页面根本不重新加载，状态一点没变。

正确做法：别依赖刷新。登录成功后直接调用页面自己的函数
（setUser / hideAuth / startApp）切换界面就行。

还有一个相关的坑：
    刚发完登录请求就去操作界面，可能被页面自己的启动流程
    （boot() 里的 /api/auth/me）晚回来一步给覆盖掉，
    于是登录框又被弹回来。
    解决办法是先等一秒让 boot() 跑完，再登录、再切换。

--------------------------------------------------
坑 5：截图出来的两张不同的图，内容一模一样
--------------------------------------------------

排查时发现两个不同页面截出来 MD5 完全相同。
于是做了一个对照实验：去截一个内容完全不同的页面（纯 JSON 接口），
看哈希是否还一样。

    哈希不同 → 截图机制是好的，问题在"被测的那个页面"
    哈希相同 → 截图机制本身有问题

这个方法叫对照实验：拿一个"肯定应该不一样"的东西去比。
比一个劲怀疑代码有效得多。
